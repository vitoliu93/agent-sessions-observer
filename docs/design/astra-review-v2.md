# Agent Session 观察台 v2：需求解决地图

## 大前提

用户要判断的是：**需求解决到哪一步，谁贡献了什么，还差什么才能完成。** 能回答这三个问题的事实才进入地图；调用工具、启动代理、等待消息不自动成为节点。

## 小前提

本例只有一条主线：字体识别提速，30 秒片处理时间降到 120 秒内，判定结果不变。

- Reviewer 提出了两条风险，已知一条是批间排序稳定性。
- Programmer 实现分片并发 C31、VLM 并发 C32/C33；首跑 8 条回归有 2 条失败；修复批间合并排序后重跑 PASS；一次性能对比为 411s → 118s。
- 后台哨兵监听产物标记；另一个 Task 子代理负责比对基线。现有材料没有给出它们的完整结论。
- 需求背景中的 330s 和本次性能对比中的 411s 不应混成同一个基线。118s 达标不自动证明所有判定结果不变。

## 结论

**放弃以代理和时间为骨架的泳道图。采用“目标 → 解决路径 → 验收结果”的地图，代理以署名出现，时间作为查询条件。**

### 1. 图式：六种节点，六种关系

#### 节点类型

| 类型 | 回答的问题 | 本例内容 | 显示方式 |
| --- | --- | --- | --- |
| 目标 | 最终要解决什么？ | 字体识别提速，判定不变 | 左侧大卡片；列出验收条件 |
| 子目标 | 哪项要求需要单独证明？ | 30 秒片 ≤120s；判定结果与基线一致 | 两张分支卡片；各自显示状态 |
| 方案与修改 | 具体改了什么？ | 分片并发 C31；VLM 并发 C32/C33；修复批间合并排序 | 普通卡片；一句动作、一个结果 |
| 风险与障碍 | 什么可能或已经妨碍完成？ | 批间排序可能不稳定；首跑回归 2/8 失败 | 风险用描边，已发生的失败用实色提示；明确区分 |
| 验证 | 用什么检查，检查到了什么？ | 性能测量 411s →118s；8 条回归重跑 PASS；基线比对 | 显示样本范围、结果和证据入口 |
| 结论 | 哪项要求已被证明，哪项还没被证明？ | 本次 30 秒样本耗时达标；判定一致性是否已证实 | 最右侧结果卡；不能只有“完成”二字 |

**节点不是一段聊天，也不是一次工具调用。** 一项修改被连续讨论十次，仍是一张卡；两次不同版本的测试，必须保留两次验证记录。子代理任务刚开始时，先建立对应的工作卡，结果栏写“尚无结果”，不要另建“派发任务”卡。

#### 边类型

每条边必须带动词，不能只用颜色表达含义。

| 边 | 方向 | 含义 |
| --- | --- | --- |
| 拆成 | 目标 → 子目标 | 独立验收的要求 |
| 采用 | 子目标 → 方案与修改 | 为满足要求选择的做法，不表示已经有效 |
| 妨碍 | 风险与障碍 → 子目标或修改 | 可能影响或已经阻止哪件事 |
| 解决 | 修复 → 风险与障碍 | 处理了哪个问题；未验证时标“待验证” |
| 检查 | 方案与修改或子目标 → 验证 | 检查哪个版本、哪项要求 |
| 支持 | 验证 → 结论 | 结论依据是什么；证据不足时不连这条边 |

不新增“主代理调用子代理”“等待完成”“收到消息”等关系。Reviewer 的排序风险与回归失败只有在内容明确对应时才合并或关联；不能因为先后出现就认定存在因果。

#### 本例默认展开内容

```text
                         ┌─ 耗时 ≤120s ─采用→ 分片并发 C31 ─────┐
字体识别提速、判定不变 ─拆成┤                  VLM 并发 C32/C33 ─┴─检查→ 411s→118s ─支持→ 本次样本耗时达标
                         └─ 判定与基线一致 ─检查→ 基线比对 ────────────────→ 有证据后才生成结论
                                  ↑
                           妨碍：批间排序风险
                                  ↑ 解决（验证后确认）
                           修复批间合并排序 ─检查→ 回归重跑 PASS
```

首跑 2/8 失败放在排序修复附近，保留“失败 → 修复 → 重验”的可展开支路。回归 PASS 能否支持“判定与基线一致”，取决于回归范围，不能自动连线。性能验证卡注明被测版本，不能仅凭图上相邻就声称某一个并发改动单独带来全部收益。

### 2. 关联：产出挂到目标，名字贴在产出上

**代理不是地图里的地点，它是工作和结论的署名。**

- 卡片底部固定显示角色与身份，例如 `提出：Reviewer · R1`、`实现：Programmer · P1`、`验证：基线比对子代理 · B1`。不同代理不能因角色相同而混成一个人。
- 风险卡挂到受影响的子目标；修改卡挂到它服务的子目标；验证卡连到被检查的目标或版本。由这些边回答“和主线有什么关系”，不再画代理归属线。
- 同一产出服务多个子目标时，只保留一张卡，连到多个目标。打开卡片可直接看到“服务哪些要求”。
- 同一卡片多人参与时，分别显示“提出、实现、验证”，不要只写“参与者”。主代理转述 Reviewer 的判断，不应把作者改成主代理。
- 点击署名，高亮此人的卡片及其通向目标的关系，其余变淡。侧栏列出“承担的事、已给出的结果、尚未回答的问题”。

**哨兵的处理规则：** 当前只知道它监听产物标记，不给它独立泳道或“挂哨兵”节点。在对应验证卡的状态中写“等待产物标记”。若它发现产物缺失、测试完成或异常退出，更新该验证卡，并署名“报告：后台检查”。“检测到标记”只能证明标记存在，不能直接写“测试通过”。若它实际委派了基线比对，地图显示“比对基线”这件事及其结果；谁委派谁放进详情，不占主图。

### 3. 布局：从左到右看解决路径，不按时钟排队

整体分为四列：

1. **目标与验收条件**：左侧固定，目标卡始终可见。
2. **方案与问题**：修改在中间，风险和失败贴近相关修改。
3. **验证与证据**：按性能、判定一致性分组，不按代理分组。
4. **已证实的结果与缺口**：最右侧，明确写“还差哪项证明”。

纵向按子目标分区。本例上方是耗时，下方是判定一致性。共同修改放在两区之间，不复制。主轴是“怎样满足验收条件”，不是“谁先说了什么”。

- 首屏保留目标、进行中的工作、未解决障碍、最新验证和结果。已结束的重试折成“失败 2 条 → 排序修复 → 重跑 PASS”，点击展开。
- 新结果出现时，只在所属区域补卡；不重新打乱整张地图。用户拖动或展开的状态保留。
- 时间放在节点详情：开始、最近更新、耗时、证据发生时间。页面底部提供可收起的历史滑条，用于查看某个时刻已知的地图。
- 历史模式醒目标“正在查看历史”，提供“回到实时”。时间不决定节点位置，也不画等距时间刻度。
- 原始对话与工具记录只在右侧证据栏查看，点击可跳到准确记录。

### 4. 实时：更新事实，不把每条消息画成新节点

#### 页面顶部固定一张“当前进展”卡

固定三行，不滚动刷聊天：

> **正在做：** Programmer 修复批间合并排序。  
> **已知道：** 首跑回归 8 条中 2 条失败。  
> **下一项验证：** 重跑回归，检查失败是否消失。

完成后替换为有范围的结果：

> **当前结果：** 本次 30 秒片耗时 118s，达到 120s 内要求。  
> **已验证：** 8 条回归重跑 PASS。  
> **仍需确认：** 基线比对是否证明判定结果不变。

这些是不同阶段的展示示例，不应同时当作当前状态。多项工作并行时最多列三项，并列出各自署名；不把等待中的任务写成正在计算。

#### 渐进填充规则

| 新观察到的内容 | 地图变化 |
| --- | --- |
| 用户给出需求 | 建目标和明确的验收条件；未说明的条件不猜 |
| 明确开始承担某项工作 | 建工作卡，署名负责人，状态“进行中” |
| 提出风险 | 建风险卡，连接受影响目标，状态“待确认” |
| 修改完成 | 更新修改卡为“已修改，待验证”，不能变成目标完成 |
| 得到测试输出 | 建验证记录，保留样本、版本、退出结果和来源 |
| 测试失败 | 验证卡标失败；影响明确时补障碍；失败记录不删除 |
| 修复并重跑 | 建新的验证记录；通过后才把对应障碍标“已解决” |
| 所有验收条件都有支持证据 | 生成目标完成结论 |

#### 最小实现要求

- 读取 JSONL 的新增完整行；半行等待下一次读取。按 session、记录位置和工具调用标识去重。子代理记录仍保存来源 session。
- 先把新增内容归入“目标、工作、问题、验证、结论”，再更新地图。每张卡有固定编号；同一工作更新原卡，不按一句话建一张卡。
- 节点至少保存：类型、短标题、状态、目标归属、按职责区分的署名、证据位置、最近更新时间。验证另存样本与被测版本；边也保存来源依据。
- 区分三种依据：“执行记录”“代理自述”“系统归纳”。模型总结不能冒充工具输出；没有来源的关系不能显示为已证实。
- 新增记录每 2 秒检查一次；普通文本最多合并 5 秒再总结。收到测试结束等关键结果时立即触发更新。地图摘要未生成完时，显示“收到新记录，摘要更新中”。
- 更新只短暂突出改变的卡片，不移动视角。顶部显示“数据读到何时”“摘要更新到何时”，防止旧摘要被误认为实时状态。
- 没有新输出不等于任务卡死。仅显示“最近收到记录的时间”；只有明确错误、超时结果或停止记录才能判失败。
- 消息相互冲突时并列证据，状态“待确认”，不能悄悄用最新一句覆盖先前测试结果。用户修改目标时保留旧验收条件的版本。

### 5. 反模式：主图绝对不要出现

1. **把派发、挂哨兵、收束、等待、收到消息当作进展节点。** 有动作不等于需求更接近完成。
2. **每个代理一条泳道。** 它把同一个问题拆散，让用户自己拼关系。
3. **把所有工具调用、文件读取、命令和原始回复铺满画布。** 原始记录必须保留，但只放证据层。
4. **没有动词的连线、只表示调用层级的紫色边、无法解释原因的重试回路。**
5. **“Reviewer 完成”“Programmer 完成”这类空结论。** 必须写审出了什么、改了什么、验证了什么。
6. **未经证实的因果线。** 时间相邻、同一代理执行，不代表前者导致后者。
7. **把方案完成、代理退出、产物标记出现写成需求完成。**
8. **把局部测试 PASS 写成全面正确。** 性能、回归和基线一致性分别验收。
9. **把 330s、411s 混作同一基线，或给没有样本范围的提速数字。**
10. **凭空补 Reviewer 的第二条风险、哨兵结果或基线比对结论。** 未知就写未知。
11. **伪造完成百分比、倒计时和健康分。** 没有明确总量，就只报已证实的条件与剩余缺口。
12. **实时刷新时整图跳动，或用聊天滚屏代替当前总结。**
13. **把 token、代理数量和调用次数放在主视觉中心。** 如需保留，放进折叠的成本详情。

**v2 的验收标准：不打开原始聊天，也能读出目标、Reviewer 的风险、Programmer 的修改、失败如何被修复、118s 证明了什么，以及哪些结论仍缺证据。**
